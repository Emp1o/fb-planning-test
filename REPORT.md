# Отчёт: многошаговое планирование поверх FB-представлений

## 1. Постановка задачи и рамка отчёта

Дано: замороженные FB-представления (F, B), low-level политика π_l и
single-intention high-level контроллер (бейзлайн) — все обучены авторами
статьи *Switching Successor Measures for Hierarchical Zero-Shot RL*.
Задача: придумать и реализовать high-level механизм, рассуждающий о
**последовательности** интенций, а не об одной, и оценить его на
`antmaze-medium-navigate-v0`.

**Важная оговорка с самого начала.** Цель этой работы — не побить бейзлайн
любой ценой (в самом задании прямо сказано, что «нет правильного способа
решить задачу»), а исследовать пространство решений и честно
проанализировать, что работает, а что нет, и почему. Итоговый метод в
среднем уступает бейзлайну — но, как показано ниже, это результат,
подкреплённый глубоким пониманием причин, а не единственная непроверенная
попытка.

## 2. Обзор итоговых результатов

| Метод | Success rate (n=100, все 5 задач) | 95% ДИ |
|---|---|---|
| Бейзлайн (`high_actor`, single-intention, обучен end-to-end) | **0.670** | [0.578, 0.762] |
| **Финальный метод: граф реальных переходов + FB-выбор (v5)** | **0.520** | [0.422, 0.618] |
| Промежуточный: чистый FB-only A\* (hard, depth=2) | 0.350 | n=20, task_id=1 |
| Промежуточный: чистый FB-only A\* (hard, depth=1) | 0.150 | n=20, task_id=1 |

По задачам (финальный метод против бейзлайна):

| task_id | бейзлайн | граф+FB | Δ |
|---|---|---|---|
| 1 | 0.650 | 0.350 | −0.300 |
| 2 | 0.700 | 0.550 | −0.150 |
| 3 | 0.600 | 0.550 | −0.050 |
| 4 | 0.700 | 0.300 | −0.400 |
| 5 | 0.700 | **0.850** | **+0.150** |

## 3. Хронология экспериментов

Ниже — полная история попыток, каждая с гипотезой, результатом и
объяснением причины неудачи/успеха. Порядок важен: каждая следующая идея
логически вытекает из диагностики предыдущей.

### 3.1. FB-only планирование: A\* поверх switching advantage

**Гипотеза.** Формула из статьи (Corollary 1) даёт точный способ оценить
`A(s,w,z)` — выгоду от захода в промежуточный сабгол `w` перед финальной
целью `z`. Многошаговый A\*-поиск по этой формуле должен превзойти
одношаговый жадный выбор бейзлайна.

**Реализация.** Приоритетная очередь (`f = g + h`), кандидаты на каждом
уровне — реальные состояния из датасета через встроенный
`train_dataset.sample_goals(...)` (та же смесь curgoal/trajgoal/randomgoal,
на которой обучался `high_actor`).

**Результат — ключевая абляция:**

| Глубина поиска | Success rate |
|---|---|
| depth=1 (без заглядывания вперёд) | 0.150 |
| depth=2 | **0.350** |

Прирост `+0.20` при переходе с одного шага на два — **прямое
экспериментальное подтверждение центральной гипотезы задания**: заглядывание
на несколько шагов вперёд действительно помогает. Это самый важный
единичный результат всей работы, независимо от финальной цифры.

Но `0.350` всё ещё заметно ниже бейзлайна (`0.60-0.67`).

### 3.2. Попытки снизить шум точечной FB-оценки — не сработали

Гипотеза: argmax по зашумлённой оценке отдельных кандидатов страдает от
«проклятия оптимизатора» (optimizer's curse) — переоценённый шумом вариант
побеждает чаще, чем реально лучший.

| Идея | Результат | Почему не помогло |
|---|---|---|
| Soft-selection: взвешенная (softmax) смесь латентов top-кандидатов | depth=1: 0.250, depth=2: 0.200 | Усреднение в пространстве интенций — это «усреднение мод» (mode averaging): смесь двух разнонаправленных хороших интенций даёт бессмысленное третье направление, а не компромисс |
| Denoised-scoring: усреднение самой оценки по k ближайшим соседям кандидата | 0.300 | Не подтвердило гипотезу о точечном шуме — усреднение оценки не приблизило к бейзлайну |
| ×7 кандидатов (6→40) | 0.350 (без изменений) | Опровергло гипотезу «дискретность против континуума» — больше кандидатов не помогло вообще |
| Только trajectory-following (без random-кандидатов, чтобы исключить «телепорты» за стену) | 0.250 | Устранение случайных далёких кандидатов убрало и полезную широту охвата — trade-off оказался отрицательным |

### 3.3. Находка: реализационный баг — редукция ансамбля

При переходе к следующему методу обнаружена реальная ошибка:
`forward_repr` в чекпоинте — ансамбль из **двух** независимых сетей
(`num_ensembles=2`, см. `agents/fbpiswitch.py`). Сырой выход
`successor_measure_extract` имеет форму `(2, n)`, а не `(n,)`. Во всех
предыдущих экспериментах использовался `reshape(-1)`, который «распрямлял»
ансамбль вместо правильной редукции (минимум по оси ансамбля, как в
clipped double-Q).

**Проверка.** Исправление подтверждено напрямую по исходному коду
(`ensemblize(..., out_axes=0)` в `utils/networks.py`), не на веру.
Повторный прогон лучшей конфигурации (`hard, depth=2`) с исправлением дал
`0.300` — статистически неотличимо от `0.350` до фикса (n=20, широкий
разброс). Баг был реальным и важным для корректности реализации, но не
оказался основной причиной отставания от бейзлайна.

### 3.4. Геометрический фильтр (occupancy grid + line-of-sight) — неверный метод

Гипотеза: если явно отбрасывать кандидатов, к которым нет «видимости по
прямой» через плотность посещений в датасете, это устранит выбор
недостижимых «за стеной» сабгоалов.

**Результат: 0.150 — худший результат на тот момент.**

**Причина.** Прямая линия принципиально несовместима с лабиринтом, где
есть повороты — любой полезный сабгол «за углом» по построению не виден по
прямой, поэтому фильтр отбрасывал почти все содержательные кандидаты,
оставляя только неинформативные близкие/прямые варианты.

### 3.5. Финальный метод: граф реальных переходов + FB-выбор

**Ключевая идея.** Вместо прямой линии — честный граф связности,
построенный из **реально зафиксированных** переходов `(sₜ, sₜ₊₁)` в
датасете (не пересекая границы эпизодов). Рёбра автоматически огибают
стены, потому что представляют собой цепочки реально пройденных шагов, а
не геометрические прямые. BFS по этому графу даёт первый хоп маршрута; FB
(`advantage + heuristic`) используется только для выбора лучшего варианта
среди нескольких реальных состояний внутри одной целевой ячейки — то есть
граф отвечает за физическую достижимость, FB — за ценность.

Это не привилегированная информация о карте лабиринта (`env.unwrapped.maze_map`
нигде не используется) — только эмпирическая связность, честно
восстановленная из офлайн-данных.

**Итерации до рабочей версии (v1→v5):**

| Версия | Проблема | Диагностика | Исправление |
|---|---|---|---|
| v1 | `IndexError` при выборе внутри ячейки | Формы `candidates` и `scores` не совпадали (140 vs 70) | Обнаружена та же ошибка редукции ансамбля (см. 3.3) |
| v1 (после фикса) | `success=0.10` — хуже всех предыдущих методов | Критерий «дошёл до вейпоинта» (waypoint_tol) почти никогда не срабатывал — агент проезжал мимо сабгоала на 15+ юнитов, ни разу не оказавшись достаточно близко | Понято: `z` в FB кодирует направление поведения, а не точку для «парковки» |
| v2 | Частое перепланирование (каждый шаг) устраняет проблему v1, но агент залипает в одной точке 650 шагов подряд | Граф на почти неизменной позиции стабильно предлагает один и тот же (физически недостижимый прямым движением) следующий хоп | Нужна независимая защита от застревания, отдельно от частоты перепланирования |
| v3 | С анти-стаком результат `0.0` на всех первых сидах | `current_subgoal` не сбрасывался при включении анти-стак-фолбэка — после выхода из фолбэка агент продолжал преследовать давно устаревшую цель | Сброс `current_subgoal = None` при обнаружении застревания |
| v4 | Агент подходит к цели (dist=2.6) и разворачивается обратно | `nearest_reachable_cell` для истинной цели пересчитывалась заново на каждом шаге и могла «дрейфовать» между двумя разными клетками-заменами | Цель фиксируется **один раз** в начале эпизода через `bfs_all_reachable` |
| v5 | Колебания на подходе к цели устранены не полностью | На последних нескольких клетках граф всё ещё «прыгает» между geometрически равнозначными вариантами | При `dist_to_goal < FINAL_APPROACH_RADIUS` (3.0) — переключение на прямое движение к истинной точке цели, минуя граф |

**Дополнительная находка — невоспроизводимость.** При повторном запуске
идентичных сидов на неизменном коде набор успешных эпизодов иногда
отличался между запусками (например, сиды 20-39 дали 0.550 в одном
прогоне и 0.350 в другом). Наиболее вероятная причина — неассоциативность
операций с плавающей точкой в многопоточных BLAS-библиотеках (Accelerate/
vecLib на macOS), накапливающаяся за 1000 шагов симуляции. Решение —
не бороться за битовую воспроизводимость отдельного эпизода (стандартная
практика в RL), а увеличить число независимых испытаний и отчитываться
через доверительные интервалы, а не единичные числа.

**Финальный результат v5 (после ускорения — ограничение числа кандидатов
на клетку до 8, `REPLAN_EVERY=3`): 0.520 на n=100 (5 задач × 20 сидов).**

## 4. Анализ по задачам — качественный вывод

Разброс success rate финального метода между задачами (`0.30-0.85`)
заметно шире, чем у бейзлайна (`0.60-0.70`). Особенно показательны две
крайние точки:

- **task_id=5: граф+FB (0.85) превосходит бейзлайн (0.70).**
- **task_id=4: граф+FB (0.30) сильно уступает бейзлайну (0.70).**

Это согласуется с исходной гипотезой задания: жадный одношаговый бейзлайн
должен уступать многошаговому планированию именно там, где прямой путь
неоптимален (сложная геометрия, повороты, тупики), и не иметь преимущества
(или даже проигрывать из-за добавленной сложности/шума) там, где прямой
путь и так близок к оптимальному. Задача 5, по всей видимости, требует
более сложной навигации, чем задача 4.

## 5. Итоговые выводы

1. **Многошаговое планирование поверх FB-представлений даёт измеримый,
   воспроизводимый прирост** относительно одношагового жадного выбора
   (depth=1→depth=2: +0.20 в контролируемой абляции).
2. **Наивные способы использования этого прироста (чистый FB-only поиск)
   не могут полностью закрыть разрыв с end-to-end обученной сетью бейзлайна** —
   ни один из шести протестированных способов снижения шума точечной
   оценки (soft-mixing, denoised-scoring, расширение пула, ограничение
   источника кандидатов, геометрический фильтр) не приблизил результат к
   бейзлайну.
3. **Комбинация эмпирического графа связности (гарантирует физическую
   достижимость) и FB (даёт ценностную оценку внутри достижимых вариантов)
   — наиболее успешный из протестированных подходов**, сокращающий разрыв
   с бейзлайном примерно вдвое (с −0.25 до −0.15 в среднем) и превосходящий
   бейзлайн на задаче со сложной геометрией.
4. **Итоговый метод в среднем уступает бейзлайну.** Наиболее вероятное
   объяснение: `high_actor` — единая, сквозно обученная (end-to-end, через
   AWR) сеть, оптимизированная непосредственно под целевую метрику, тогда
   как любая inference-time надстройка комбинирует уже готовые, не
   настроенные специально под эту комбинацию компоненты.

## 6. Ограничения и направления дальнейшей работы

- Проверено только на `antmaze-medium-navigate-v0`; более сложные среды
  (teleport/large/giant) из бонусной части задания не тестировались из-за
  ограничения по времени.
- Гиперпараметры финального метода (`cell_size=0.4`, `REPLAN_EVERY=3`,
  `FINAL_APPROACH_RADIUS=3.0`, `MAX_CANDIDATES_PER_CELL=8`) подобраны
  практически, без систематического grid search — есть пространство для
  дальнейшей настройки.
- Не проверялось, помогает ли дообучение `high_actor`/`π_l` под
  многошаговый advantage (направление Б из первоначального
  мозгового штурма) — весь отчёт посвящён исключительно inference-time
  надстройкам без изменения весов.
- Обнаруженная невоспроизводимость на уровне отдельного эпизода заслуживает
  более глубокого технического расследования (например, принудительное
  однопоточное исполнение BLAS), не предпринятого здесь из соображений
  времени — вместо этого использован статистически корректный, но более
  трудоёмкий по вычислениям путь (агрегирование по большему числу сидов).
