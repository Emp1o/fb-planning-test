# Многошаговое планирование поверх FB-представлений — финальное решение

> **Примечание:** `README.md` в этой папке — оригинальный, от авторов
> статьи (описание метода SSM, ссылки, цитирование) — оставлен без
> изменений. Этот файл (`SOLUTION.md`) — инструкция конкретно по моему
> решению тестового задания.

## 1. Соответствие условиям задания (проверено построчно)

| Требование задания | Как выполнено |
|---|---|
| Использовать F, B, π_l и датасет, способ — на усмотрение | Финальный метод (`graph_navigator.py`) использует: `B` — для эмбеддинга сабгоалов; `π_l` (`actor`) — для исполнения; `F` (через `successor_measure_extract`) — для выбора лучшего кандидата внутри ячейки графа; граф связности строится **только** из реальных переходов офлайн-датасета |
| Без генеративной модели мира/траекторий | Граф — не генеративная модель, а справочная структура (список реально зафиксированных переходов), ничего не синтезирует |
| Без дополнительного взаимодействия со средой для обучения | Граф строится офлайн из `train_dataset`; никаких новых данных из среды не собиралось |
| F, B, π_l не обязательно переобучать | Не переобучались — использовались как заморожены, ровно как выданы в чекпоинте |
| Не использовать привилегированную информацию (карту стен и т.п.) | Явно проверено и отклонено: `env.unwrapped.maze_map` **не используется** нигде в финальном коде — только эмпирическая связность из датасета |
| Основная среда — antmaze-medium-navigate-v0 | Все результаты ниже — на ней |
| Несколько сидов, исключить случайность | 100 испытаний на метод (5 задач × 20 сидов), доверительные интервалы; отдельно задокументирован и учтён источник шума (см. п. 5) |

## 2. Структура репозитория

```
switching-successor-measures-main/
├── agents/, utils/, main.py           ← из оригинального репозитория (не менялись)
├── checkpoints/
│   ├── flags.json
│   └── params_1000000.pkl             ← переименованный из params.pkl
├── astar_planning.py                  ← базовые FB-функции (использует graph_navigator.py)
├── graph_navigator.py                 ← ФИНАЛЬНЫЙ метод: граф + FB
├── run_baseline_eval.py               ← оценка бейзлайна (все 5 задач)
├── run_astar_eval.py                  ← оценка промежуточного метода (чисто FB A*, для истории экспериментов)
├── run_graph_eval.py                  ← оценка ФИНАЛЬНОГО метода (все 5 задач)
├── run_compare_eval.py                ← оба метода (бейзлайн + graph+FB) ОДНИМ запуском, с общей сравнительной таблицей
├── SOLUTION.md                          ← этот файл
└── REPORT.md                          ← полный отчёт с хронологией экспериментов
```

**Про `run_compare_eval.py`:** делает то же самое, что `run_baseline_eval.py` и `run_graph_eval.py` вместе, но за один запуск — считает `z_goal` один раз на задачу и переиспользует для обоих методов, а в конце печатает единую сравнительную таблицу (по задачам + общий итог с доверительными интервалами), без необходимости вручную сводить два отдельных вывода. Удобен, если нужен **один** прогон для итоговых чисел в отчёт. `run_baseline_eval.py`/`run_graph_eval.py` по отдельности всё ещё полезны, если нужно перепрогнать только один метод (например, при подборе гиперпараметров графового метода — не нужно каждый раз ждать бейзлайн заново).

## 3. Установка и запуск

```bash
python3.12 -m venv venv        # именно 3.12 — для 3.13 нет готового wheel labmaze на Mac
source venv/bin/activate
python3 -m pip install --upgrade pip
python3 -m pip install "jax>=0.4.38" "flax>=0.10.2" "distrax>=0.1.5" \
    "gymnasium==0.29.1" "ml_collections>=1.1.0" "ogbench==1.1.4" \
    "h5py==3.12.1" "wandb>=0.19.11" numpy

cd switching-successor-measures-main
mv checkpoints/params.pkl checkpoints/params_1000000.pkl   # если ещё не переименован

python3 run_compare_eval.py      # ~25-35 минут — оба метода сразу, с общей таблицей в конце
# ЛИБО по отдельности:
python3 run_baseline_eval.py     # ~2-5 минут
python3 run_graph_eval.py        # ~25-35 минут (5 задач × 20 сидов, ~15 сек/эпизод)
python3 run_astar_eval.py        # ~5-8 минут (опционально, для полноты истории)
```

Датасет OGBench скачается автоматически при первом запуске.

## 4. Финальные результаты (antmaze-medium-navigate-v0, все 5 задач, n=100 на метод)

| Метод | Success rate | 95% ДИ |
|---|---|---|
| Бейзлайн (`high_actor`, обучен end-to-end, single-intention) | **0.670** | [0.578, 0.762] |
| **Финальный метод: граф реальных переходов + FB-выбор** | **0.520** | [0.422, 0.618] |
| Промежуточный: чистый FB-only A\* (hard, depth=2) | 0.350 | n=20, только task_id=1 |

### По задачам (финальный метод):

| task_id | бейзлайн | граф+FB |
|---|---|---|
| 1 | 0.650 | 0.350 |
| 2 | 0.700 | 0.550 |
| 3 | 0.600 | 0.550 |
| 4 | 0.700 | 0.300 |
| 5 | 0.700 | **0.850** |

**Ключевой вывод:** финальный метод в среднем уступает бейзлайну, но систематически **превосходит** его на задаче с наиболее сложной геометрией пути (task_id=5), что качественно подтверждает исходную гипотезу задания — многошаговое планирование полезно именно там, где прямой жадный путь неоптимален.

## 5. Известные ограничения (для честности в отчёте)

- **Невоспроизводимость на уровне отдельного эпизода.** При повторном запуске идентичных сидов на одном и том же коде набор успешных эпизодов иногда отличался (вероятно, неассоциативность операций с плавающей точкой в многопоточных BLAS-вычислениях на CPU, накапливающаяся за 1000 шагов симуляции). Скомпенсировано увеличением числа независимых испытаний (n=100) и отчётностью через доверительные интервалы вместо единичных чисел.
- **Проверено только на antmaze-medium-navigate-v0.** Более сложные варианты (teleport/large/giant) из бонусной части задания не тестировались из-за ограничения по времени.
- **Абляция depth=1 vs depth=2 (в run_astar_eval.py-подобном коде) показала, что многошаговое планирование само по себе даёт устойчивый прирост** (0.15 → 0.35 в FB-only варианте) — это ключевое экспериментальное подтверждение центральной гипотезы задания, независимо от финальной цифры графового метода.
